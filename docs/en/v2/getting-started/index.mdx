Ridge installs JavaScript packages from a **content-addressed store**. Every tarball is hashed, written once, and linked into projects. The lockfile is the source of truth: if the graph cannot be reproduced, the install fails.

<Callout type="info" title="Who this is for">
If you maintain a monorepo, care about CI determinism, or have been bitten by phantom dependencies, start here. If you just need a command, skip to [Installation](/en/docs/v2/getting-started/installation).
</Callout>

## What Ridge does

- Resolves a dependency graph from `package.json` and `ridge.lock`
- Fetches packages into a global store keyed by integrity hash
- Links those packages into each project with a strict `node_modules` layout
- Refuses to proceed when the lockfile and the registry disagree

It does **not** patch `require` at runtime, rewrite your source, or invent a new package format. The output of `ridge install` is a normal Node project.

## Why another package manager

npm, Yarn, and pnpm all work. Ridge exists for three constraints those tools treat as optional:

1. **Bytes are identity.** Two packages with the same integrity hash are the same package. The store never keeps a second copy.
2. **The lockfile is a contract.** A dirty lockfile is a failed install, not a warning.
3. **Workspaces nest.** A package inside a package is still a workspace. Hoisting never crosses a workspace boundary unless you say so.

Read [Content addressing](/en/docs/v2/concepts/content-addressing) and [Workspaces](/en/docs/v2/concepts/workspaces) when you want the model, not the commands.
